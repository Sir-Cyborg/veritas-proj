SECURE APPLICATION DEVELOPMENT PROCEDURE
Corporate Banking Group


1. Introduction

This procedure defines the mandatory operational steps to be followed during the
development of software applications in order to ensure security-by-design and
security-by-default principles.

The procedure complements the Secure Software Development Policy and provides
practical instructions for development teams.


2. Purpose

The purpose of this procedure is to:
- Reduce the introduction of security vulnerabilities during development
- Ensure consistent implementation of security controls
- Support compliance with internal and regulatory security requirements


3. Scope

This procedure applies to:
- All internally developed applications
- Applications developed by external vendors on behalf of the bank
- Maintenance and enhancement activities on existing applications


4. Roles and Responsibilities

4.1 Development Team  
Responsible for implementing secure coding practices and remediation of vulnerabilities.

4.2 Application Security Team  
Provides guidance, reviews security artifacts, and validates security controls.

4.3 Project Manager  
Ensures that security activities are planned and tracked throughout the project lifecycle.


5. Secure Development Activities

5.1 Security Requirements Definition  
During the requirements phase, the development team must:
- Identify data types processed by the application
- Define authentication and authorization requirements
- Identify regulatory constraints (e.g. data retention, auditability)

All security requirements must be documented and approved before design activities begin.


5.2 Threat Modeling  
For medium and high criticality applications:
- A threat modeling session must be performed
- Potential attack vectors must be identified
- Mitigation strategies must be documented

Threat models must be reviewed by the Application Security Team.


5.3 Secure Coding Practices  
Developers must:
- Follow approved secure coding guidelines
- Avoid hard-coded credentials
- Validate all user inputs
- Implement proper error handling and logging

Use of insecure or deprecated libraries is prohibited.


5.4 Code Review  
Peer code reviews must be performed for all security-relevant components.
Security-related findings must be tracked and resolved before release.


6. Security Validation

Before deployment:
- Static code analysis must be executed
- Identified vulnerabilities must be remediated or formally accepted
- Security test results must be documented


7. Exceptions

Any deviation from this procedure requires formal approval from the Application
Security Team and must be documented.


8. Procedure Review

This procedure is reviewed annually or upon significant changes to development
standards or threat landscape.
